1. 프로젝트 배경, 목표 및 비즈니스 가치

1.1 배경

항공사 정비통제실에는 운항 중이나 지상에서 발견한 결함 신고가 계속 들어온다. 신고는 "상승 중 객실에서 퀴퀴한 냄새가 남"처럼 자연어로 들어오고, 어느 정비 부서가 맡을지는 통제 담당자가 경험으로 판단한다.

  • 같은 기체에서 최근 반복된 결함인지 매번 이력을 찾아봐야 한다.
  • 증상이 두 계통에 걸쳐 보이면 부서 판단이 사람마다 다르고, 잘못 배정되면 재배정까지 시간이 든다.
  • 왜 그 부서로 보냈는지 근거가 기록으로 남지 않는다.

1.2 목표와 범위

신고가 들어오면 같은 기체의 수리이력과 유사 결함 사례(SDR)를 근거로 담당 부서를 정하고, 근거와 함께 배정한다. 근거가 부족하거나 판단이 엇갈리면 자동 배정을 멈추고 사람 검토로 넘긴다.

배정 단위정비 부서 8개: AVI 항전, ELE 전기, ENG 엔진, HYD 유압·착륙장치, SYS 기계 계통, STR 구조, CAB 객실, FCS 비행 조종

1.3 비즈니스 가치

대상은 항공사 정비본부와 MRO(정비 위탁) 업체의 정비통제 조직이다(B2B).

2.2 핵심 처리 흐름

  1. 신고자가 요청을 보내면 Spring이 기체 마스터와 대조한다. 누락·충돌이면 아무것도 저장하지 않고 422(NEEDS_SUPPLEMENT)로 응답한다.
  2. 통과하면 요청을 QUEUED로 저장하고 202를 돌려준다. 커밋 후 실행 ID를 새로 만들고, 검색 범위를 기록한 뒤 위임 토큰과 함께 실행 요청을 큐에 넣는다.
  3. AI 서버가 LLM1로 초기 분류한다. 증상만 보고 계통(ATA)을 먼저 정하고, 그 계통의 같은 기체 이력으로 충분하면 바로 배정 결과를 만든다.
  4. 부족하면 LLM2가 SDR·AMM을 조사하고 LLM3가 검토한다. 보완이 필요하면 최대 2회 재조사한다.
  5. AI 서버는 근거 원문을 다시 확인한 뒤 결과 이벤트를 보내고, Spring이 근거 ID와 부서를 검증한 뒤 배정한다.
  6. 정비팀이 수락하면 끝나고, 거절하면 사람 검토로 넘어간다. 통제사는 수동 배정하거나 종결한다.

2.3 Agent 설계: State와 Graph

요청 하나를 처리하는 동안 노드들이 함께 쓰는 상태(GraphState)를 두고, 노드는 상태를 읽어 바뀐 필드만 돌려준다. 모든 출력 모델은 정의되지 않은 필드와 빈 문자열을 거부하고, 형식 오류가 나면 오류 내용을 알려 1회 다시 받는다.

필드타입채우는 곳과 의미

classificationClassification | NoneLLM1. ATA 2자리, 연결한 수리이력 ID, 충분 여부, 제안 부서(충분일 때 필수), 이유

Agentic 요소는 네 가지다. LLM2·LLM3가 매 단계 다음 행동(도구 호출·마무리·보류)과 도구를 스스로 고른다. LLM3가 LLM2 결과를 검토해 부족하면 무엇을 더 볼지 지정해 되돌린다. 판정에는 도구 결과에 실제로 있던 근거만 쓴다. 근거가 맞지 않거나 한도를 넘으면 이유 코드와 함께 스스로 멈추고 사람에게 넘긴다.

2.6 레퍼런스 아키텍처와 다른 점

강의 레퍼런스 아키텍처는 business-mcp가 Spring 내부 API(/internal/**)를 거치도록 정한다. 우리 구현은 business-mcp가 조회 전용 계정(mro_business_reader)으로 DB를 직접 읽고, Spring에는 /internal/** 경로가 없다. 업무 규칙이 MCP로 새지 않도록 다음 장치를 두었다.

  • 조회 전용 계정에 필요한 테이블만 권한을 주고, repair_requests는 8개 컬럼만 연다(V6). 신고자 ID는 열지 않는다.
  • 도구 호출은 읽기 전용 트랜잭션에서만 실행하고, 서버 시작 시 쓰기 권한이 있는 계정이면 실행을 거부한다.
  • 모든 호출에 실행별 위임 토큰이 필요하고, 토큰의 요청 ID와 다른 요청은 조회할 수 없다. 상태 변경과 배정은 Spring만 한다.
결정 · 유지. MCP 도구는 모두 조회 전용이라 Spring을 거쳐도 얻는 업무 규칙 보호가 없고, 오히려 Spring에 도구별 내부 API와 응답 변환이 생긴다. 대신 컬럼 단위 권한(V6), 읽기 전용 트랜잭션, 실행별 위임 토큰과 요청 ID 대조로 같은 경계를 지켰고, 실제 실행에서 토큰 없는 호출 401·다른 요청 조회 FORBIDDEN을 확인했다(4.4).

서버 구성

business-mcp(8101)와 rag-mcp(8102)는 공통 기반(src/mro_mcp/common)을 같이 쓴다: 위임 토큰 검증 미들웨어, 읽기 전용 DB 연결, 공통 응답 형식(status, request_id, context_version, trace_id, counts, next_cursor, warnings, error, items), 오류 코드, 상태 확인(/health, /health/ready, /health/live). 모든 도구는 읽기 전용이다. AI 서버의 MCP 클라이언트 하나가 두 서버에 연결하고, LLM1은 business 도구만, LLM2·LLM3는 두 서버 도구를 모두 받는다.

위임 인증과 검색 범위

  1. 요청이 저장되면 Spring이 실행 ID를 새로 만들고 rag_request_contexts에 검색 범위를 기록한다: 요청 ID, 버전, 신고자·항공사, 모델 키(하이픈 제거), 준비된 데이터 버전과 색인, 만료 1시간.
  2. Spring이 서버별 위임 토큰 2개(HS256, 발급자 mro-backend, 대상 mro-business·mro-rag, 유효 10분)를 AMQP 헤더(x-mro-business-token, x-mro-rag-token)로 보낸다.
  3. AI 서버는 토큰을 프롬프트나 체크포인트에 남기지 않고 MCP 호출의 Authorization 헤더로만 쓴다.
  4. MCP 서버는 서명·대상·만료를 확인하고, 도구 입력의 요청 ID가 토큰과 다르면 거부한다. rag-mcp는 기록된 범위가 활성·미만료·같은 버전인지도 확인한다.

SDR 운항사는 미국 항공사뿐이라 검색 범위는 항공사 필터 없이 정확한 모델만으로 정했다(운항사 NULL, 매핑 버전 backend-v1-model-only).

AI 서버는 근거 원문 일부가 실제로 가져온 원문 안에 있는지, 부서가 배정 가능한지도 확인한다. 모델이 발췌를 의역하면 조회한 근거의 원문으로 바꾸고, 조회하지 않은 ID는 탈락시킨다. Spring은 근거가 없거나 확인되지 않는 ID가 있으면 배정하지 않고 사람 검토(VALIDATION_FAILED)로 넘긴다.

오류와 예외 처리

  • 결과 상태 OK, NO_DATA, NO_MATCH, NEEDS_INPUT, ERROR와 오류 코드(INVALID_ARGUMENT, FORBIDDEN, MISSING_SCOPE, INDEX_NOT_READY, INVALID_CURSOR, CONTEXT_VERSION_CONFLICT 등), 재시도 가능 여부를 함께 돌려준다.
  • MCP 서버: 문장 실행 8초, 입력 2,000자, 목록 요약 30개 제한, 서명된 커서(30분 만료).
  • AI 서버: 도구 호출 10초 제한, 일시 오류와 retryable=true일 때만 1회 재시도. 처리하지 못한 예외는 FAILED 이벤트로 보내고 Spring이 SYSTEM_ERROR로 사람 검토에 넘긴다.

Spring은 발행 때 브로커 확인을 기다리고, AI 서버는 prefetch 1로 받아 최종 이벤트 발행이 확인된 뒤에만 ack한다. 처리 중 종료되면 메시지가 다시 전달된다. Spring은 30초마다 5분 넘게 진행 중인 요청을 찾아 사람 검토로 바꾼다.

DLQ 증빙: AI 서버를 중지한 상태에서 요청을 접수했다.

  … 5분 동안 아무도 실행 요청을 가져가지 않음 (mro.agent.run TTL 5분)
  → mro.agent.run.dlq → Spring 소비 → 사람 검토 전환

6.1 주요 문제와 해결 방법

문제해결 방법
SDR 운항사가 미국 항공사뿐이라 국내 항공사 기준 검색이 안 됨 (검색 0건, AI가 결과를 범위 위반으로 폐기)검색 범위를 항공사 없이 정확한 모델 기준으로만 정함(운항사 NULL, 매핑 버전 기록). MCP와 AI 쪽 범위 검사 모두 이 정책을 허용
ATA 27(비행 조종)을 맡을 부서가 없음비행 조종 부서(FCS)를 추가하고 수리이력 78건, 시나리오 S23, 기술자료 부서 매핑을 보강
접수 누락·충돌을 어디서 처리할지AI 작업을 만들기 전에 Spring이 422로 필드별 보완 안내. 사람 검토로 보내지 않음
LLM 처리 시간이 길어 HTTP 동기 호출이 불안정RabbitMQ로 바꾸고 DLQ, TTL, 시간 초과 감시로 실패를 사람 검토로 전환
MCP가 어떤 요청의 범위로 검색해야 하는지 전달 방법 (rag-mcp 전부 401)Spring이 실행마다 검색 범위를 기록하고 서버별 위임 토큰을 발급, MCP가 토큰과 기록을 함께 검증
business-mcp가 요청 정보를 읽을 권한이 없음필요한 8개 컬럼만 조회 권한을 여는 Flyway V6. 신고자 ID는 비공개
LLM1이 같은 기체의 무관한 이력을 근거로 바로 배정 (예: 브레이크 진동 ↔ 도어 보틀 압력)증상만으로 ATA를 먼저 정하고 그 ATA 이력만 비교, 연결 이력마다 공통 대상 표현을 코드로 확인, 확인 안 되면 조사로 넘김
조사 단계가 RAG를 호출하지 않고 무관한 이력을 근거로 인용LLM1이 연결하지 않은 이력은 LLM2에 숨기고 근거로 불인정, 근거 없이 결론을 쓰면 2회까지 반려. 이후 조사 경로 16건 모두 SDR 근거
모델 입력이 158,418 토큰으로 한도(128K) 초과근거 원문·핵심 필드만 전달, 이력은 인용분 + 최근 20건, 도구 응답은 상태·범위·ID만
SDR·JASC 검색 대부분 0건 (모든 단어 일치 방식, 한국어 검색어)넓은 검색은 단어 하나라도 맞으면 순위로, 도구 설명에 영어 핵심어 예시, 확인 안 된 JASC 힌트 제외
모델 출력 형식 오류로 실행 실패 (gpt-5.4-mini 23건 중 11건)형식 오류 시 오류 내용을 알려 1회 재요청, 의미가 같은 입력(빈 선택 필드 등)은 허용. 실행 실패 1건 이하로 감소
LLM이 없는 근거 ID나 원문을 만들 위험AI 서버가 발행 전 다시 조회하고 원문 포함 여부를 대조(의역된 발췌는 원문으로 교체), Spring이 배정 직전에 한 번 더 검증
rag-mcp 이미지 19.3GB, 빌드 지연CPU 전용 PyTorch 고정과 빌드 캐시 분리로 2.03GB, 빌드 57초
대용량 RAG 데이터를 팀 공유 DB에 넣는 방법공유 DB에 직접 넣지 않고 데이터만 담은 덤프를 Backend가 복원, 건수·해시 확인
저장소마다 임베딩 방식이 다를 위험모델·리비전·접두어·창 크기를 한 설정으로 고정하고 manifest에 기록

6.3 한계

한계영향과 개선 방향
판단 편차같은 시나리오도 실행마다 경로·부서가 달라질 수 있다(예: S05·S06이 실행에 따라 바로 배정 또는 조사 경로). 시나리오별 반복 실행으로 비율 평가 필요
신규 증상의 부서 선택S07(항전 기대 → 사람 검토), S15(기계 계통 기대 → 엔진)처럼 계통이 겹치는 증상의 부서 선택이 기대와 다를 수 있다. 증상 → ATA → 부서 대응을 검증에 더 반영
검색 언어SDR 전문검색은 영어 단어만 쓴다. 한국어 신고는 AI가 영어 핵심어로 바꿔야 하며, AMM 의미 검색만 한국어를 직접 받는다
Backend 근거 검증 범위근거 ID의 존재와 기종 일치만 확인하고 증상과의 관련성은 AI 쪽 검증에 의존
AMM은 SDR의 인용 번호와 맥락실제 매뉴얼 절차와 적용성은 확인할 수 없음. 정식 매뉴얼 연동 시 적용성 검증 추가
수리이력·계정이 목업실제 운영 분포와 다를 수 있음. 실제 정비 이력으로 재검증. 시나리오 결과는 서비스 흐름 검증이며 실제 분류 정확도를 뜻하지 않음
business-mcp DB 직접 조회레퍼런스 아키텍처와 다름(2.6). 의도한 선택으로 유지하되 권한·토큰으로 경계 보장
