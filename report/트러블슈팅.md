# 트러블슈팅

통합 과정에서 실제로 겪은 문제를 현상 · 원인 · 조치 · 결과 순서로 정리했다.
문제는 발생 위치에 따라 ① 연결·계약, ② 데이터·검색, ③ AI 판단, ④ 빌드·운영으로 나눈다.

## 상세

### ① 연결·계약

**1. business-mcp 업무 조회 실패 (팀 논의 C04)**
- 현상: B01(접수 확인)·B02(수리이력)·B03(부서)이 모두 `UPSTREAM_UNAVAILABLE`.
- 원인: 세 도구 모두 먼저 `repair_requests`에서 요청을 확인하는데, Flyway V4가 조회 전용 계정에 기체·항공사·부서·수리이력만 허용했다.
- 조치: Flyway V6로 `repair_requests`의 확인용 8개 열(`id`, `tail_number`, `aircraft_model`, `airline_code`, `symptom_text`, `status`, `created_at`, `version`)만 허용했다. 신고자 ID·요약 등은 계속 막았다.
- 결과: 실제 요청으로 B01~B03 정상 응답. 열 단위 권한은 테스트로 확인.

**2·3. MCP 인증과 실행 범위 (팀 논의 C01)**
- 현상: rag-mcp는 모든 호출이 401, business-mcp는 반대로 인증이 없었다.
- 원인: rag-mcp는 backend가 서명한 요청별 토큰과 `rag_request_contexts`의 검색 범위를 요구하는데, backend가 둘 다 만들지 않았다(컨텍스트 0건, 실행 메시지에 토큰 없음).
- 조치
  - backend `McpDelegationService`: 실행마다 `run_id`를 만들고 검색 범위를 등록한 뒤 business·rag용 토큰(HS256, aud 분리, 10분)을 RabbitMQ 헤더 `x-mro-business-token`·`x-mro-rag-token`으로 전달.
  - business-mcp: 같은 방식으로 토큰을 검증하고, 토큰에 적힌 `request_id`의 접수만 조회.
  - AI 서버는 기존에 제안된 헤더 방식(`MCP_DELEGATION_TRANSPORT=amqp_headers`)을 그대로 사용해 코드 변경이 없었다.
- 결과: 무토큰·다른 서버용 토큰은 401, 다른 요청 조회는 `FORBIDDEN`. 실제 실행에서 MCP 인증 실패 0건.

**4. 프론트·백엔드 응답 형식 불일치**
- 현상: 422 보완 안내가 일반 오류로 표시되고, 판단 근거·처리 단계가 비어 있었다.
- 원인: 프론트가 에러를 `data.code`로 읽었지만 백엔드는 `{ error: { code, details } }`로 감싸 보냈다. 판단 기록(trace)도 구조가 완전히 달랐고, 정비팀·관리자 화면은 목업 데이터만 사용했다.
- 조치: "백엔드가 기준" 원칙으로 프론트 타입을 백엔드 DTO와 1:1로 맞추고, 목업을 제거해 모든 화면을 실제 API에 연결했다.

### ② 데이터·검색

**5·6. 운항사 불일치로 검색 0건 (팀 논의 C02)**
- 현상: RAG 검색이 0건이거나, 결과가 와도 AI가 "SDR 운항사 범위가 일치하지 않습니다"로 버렸다.
- 원인: 검색 범위가 "항공사 × 기종"이었는데 우리 항공사 코드는 SDR 원본 운항사(AALA, DALA 등)에 없다.
- 조치: 시연 정책으로 운항사를 비우고 기종만 고정했다. MCP는 운항사가 없으면 필터를 적용하지 않고(`operator_filter_applied=false`), AI 쪽 검사도 이를 허용하도록 고쳤다. 운항사가 지정된 경우의 엄격한 검사는 유지했다.

**7. 키워드 검색 0건**
- 현상: LLM2의 SDR·JASC 검색이 대부분 `NO_MATCH`, 도구 예산을 빈 검색에 소진했다.
- 원인: 전문검색이 검색어의 **모든 단어**가 있어야 맞는 방식(`websearch_to_tsquery`)이었고, 원문은 영어인데 AI가 한국어나 긴 문장으로 검색했다.
- 조치: 넓은 검색(explore)은 단어가 하나라도 맞으면 많이 맞는 순으로 돌려주게 바꾸고, 정확 검색(exact)은 구절 검색을 유지했다. 도구 설명에 "원문은 영어, 영어 핵심어 2~5개" 예시를 넣었다(AI는 도구 설명을 읽고 도구를 고른다).
- 결과: 이후 실행에서 SDR·JASC·AMM 검색 응답이 모두 OK.

**8. ATA 27 담당 부서 부재**
- 원인: 부서 7개의 담당 ATA에 비행 조종(27장: 플랩·슬랫·러더·ELAC 등)이 빠져 있었다.
- 조치: FCS(비행 조종) 부서와 계정, FAA SDR의 실제 A320 계열 ATA 27 결함을 바탕으로 한 수리이력 78건, 반복 결함 시나리오 S23을 추가했다. 기술자료 복원 마지막에 문서별 담당 부서를 현재 부서 매핑으로 다시 계산하는 단계를 넣어 ATA 27 문서 9편을 FCS에 연결했다(전달본 무결성 검증에는 영향 없음).

### ③ AI 판단

**9. LLM1의 무관한 이력 연결**
- 현상: 브레이크 진동에 "도어 보틀 압력" 이력을, 비상구 표시등에 "구명조끼·손전등" 이력을 연결해 구조팀·객실팀에 바로 배정했다. 계통을 이력에 맞춰 ATA 52로 고르기도 했다.
- 원인: 모델이 같은 기체 이력 약 80건을 한 번에 보고 "같은 기체"라는 이유만으로 연결했다. 프롬프트의 "같은 ATA·한 단어만 같은 이력은 연결하지 않는다" 규칙을 지키지 못했다.
- 조치(프롬프트가 아니라 구조로 해결)
  1. 증상 문장만 보고 ATA 후보 1~3개를 먼저 고른다(이력을 보기 전).
  2. 그 ATA의 이력만 보여준다. 없으면 모델 호출 없이 조사 단계로 넘긴다.
  3. 연결 이력마다 "증상과 이력 문장에 둘 다 그대로 있는 대상 표현"을 적게 하고, 코드가 실제로 두 문장에 있는지 확인한다. "착륙 후", "신고" 같은 일반 표현은 인정하지 않는다.
  4. 확인되지 않은 바로 배정은 사람 검토가 아니라 조사(LLM2)로 넘긴다.
- 결과: S08·S10이 조사 경로로 넘어가 정답 부서(ELE·HYD)에 배정. 반복 결함 S23은 FLAP SYS 1 FAULT 이력 2건만 연결해 FCS에 바로 배정.

**10. 모델 입력 한도 초과**
- 현상: 조사 단계에서 `context_length_exceeded`(158,418 토큰 > 128K).
- 원인: 다음 행동을 고를 때마다 LLM1이 읽은 이력 전체, 각 도구 응답 전체, 관찰 결과 전체를 중복해서 넣었다.
- 조치: 근거 원문(1,500자)과 핵심 필드만 전달하고, 이력은 인용분 + 최근 20건, 도구 응답은 상태·범위·ID만 넣었다. 전체 기록은 검증용으로 내부에 그대로 둔다.

**11. 조사 단계의 조기 종료**
- 현상: "도구 호출 한도 안에 조사를 마치지 못했습니다", "현재 기체 이력에서 관련된 과거 문제를 충분히 확인할 수 없다"로 사람 검토.
- 원인: 이미 받은 이력을 최대 5번 다시 조회해 예산을 소진했고, 멈춤 기준이 "현장 관찰을 확인할 수 없으면 멈춤"처럼 너무 넓었다. 이력 없는 신규 증상에서 "이력 없음"을 멈출 이유로 썼다.
- 조치: 도구 선택은 AI에게 그대로 두고 실패 지점만 막았다.
  - 같은 도구·같은 인자 반복 호출 차단, LLM1이 연결할 이력이 없다고 본 경우 이력 도구 미제공
  - 고정 확인 호출(B01·B03)은 예산에서 제외
  - 결론 조건(ATA·담당 부서·근거 1건 이상)과 멈춤 조건(근거 없음·부서 결정 불가) 명시
  - 근거와 부서 후보가 있는데 멈추면 1회 반려, 예산이 끝나도 근거가 있으면 결론 작성
- 결과: 조사 → 검토 → 배정까지 완주(S08 ELE, S10 HYD, S21 HYD 등).

**12. 모델 업그레이드 후 형식 오류**
- 현상: `gpt-5.4-mini`로 바꾸자 23건 중 11건이 수 초 만에 실행 실패.
- 원인: 모델이 분류 결과와 "정보 부족" 사유를 동시에 채웠고, "둘 중 하나만"이라는 pydantic 규칙에 걸려 실행 전체가 끝났다. 형식 오류에 재시도가 없었다.
- 조치: 모든 LLM 출력이 형식 검증에 실패하면 오류 내용을 알려주고 1회 다시 받도록 했다. 분류 결과가 있으면 사유는 무시하도록 규칙을 완화했다.
- 결과: 실행 실패 11건 → 1건.

**17~20. 조사 단계가 실제로 근거를 찾게 만들기**

최종 보고서용 데이터를 모으며 실행 기록을 확인하던 중, 조사 경로로 배정된 건들의 근거가 실제 검색 결과가 아니라는 사실을 발견했다. 전체 시나리오 실행 동안 rag-mcp 호출이 0회였다.
- 원인: LLM1이 "관련 없음"으로 판단한 같은 기체 이력(최근 20건)이 LLM2 입력에 남아 있었고, 결론 조건이 "근거 1건 이상"이어서 모델이 검색 없이 그 이력을 인용했다. 예를 들어 브레이크 진동(S10)의 근거가 "상부 동체 조명" 이력이었다. 부서는 맞았지만 근거는 무관했다.
- 조치
  - LLM1이 연결하지 않은 이력은 LLM2에 보여주지 않고, LLM1 판단문에 ID가 적혀 있어도 근거로 인정하지 않는다.
  - 결론 조건을 "이번 조사에서 조회한 SDR·AMM 사례, 또는 LLM1이 연결한 이력"으로 바꾸고, 근거 없이 결론을 쓰려 하면 2회까지 반려한다.
  - 의역된 발췌는 조회한 근거의 원문으로 교체하고, 확인되지 않은 JASC 힌트는 검색 전에 제외한다. 선택 필드의 빈 문자열은 `null`로 해석한다.
- 결과: S10이 `brake vibration taxi`로 SDR 5건을 찾고, 그중 2건을 근거로 조사안을 작성했다. 검토(LLM3)가 PASS하고, 최종 재검증에서 `get_evidence`(R05)로 두 근거의 원문을 다시 확인한 뒤 HYD에 배정했다(아래 "AI Agent 실행 증빙" 참고).

### ④ 빌드·운영

**13. 실패 원인 은닉**
- AI 서버는 보안상 실패 이벤트에 `AI_EXECUTION_FAILED` 같은 코드만 남긴다. 원인은 같은 요청을 디버그 스크립트로 재현해 예외를 확인했다. 이 방법으로 OpenAI 키 오류(401), 입력 한도 초과, 형식 오류를 특정했다. 서버 로그에 예외 종류를 남기는 보강은 남은 과제다.

**15. rag-mcp 이미지 19.3GB**
- 원인: 질의 임베딩은 CPU로 하지만, `sentence-transformers`가 끌어온 Linux용 PyTorch 기본 배포본이 CUDA를 포함했다(NVIDIA 패키지 15개, 3.3GB). `uv` 다운로드 캐시도 이미지 레이어에 함께 저장돼 패키지가 두 번 들어갔다.
- 조치: Linux에서 PyTorch를 CPU 전용 저장소(`2.14.1+cpu`)에서 받도록 고정하고, 캐시를 BuildKit 캐시로 분리했다.
- 결과: 이미지 19.3GB → 2.03GB, 깨끗한 빌드 57초, 코드 변경 후 재빌드 8초. 동작은 동일(CUDA 미사용).

**16. 프론트 흰 화면**
- 원인: 타입 검사(`vue-tsc -b`)가 `src`에 `.js` 파일을 생성했고, Vite가 import 경로를 그 파일로 캐시했다. 파일을 지우자 모듈을 찾지 못했다.
- 조치: `tsconfig.app.json`에 `noEmit`을 넣어 다시 생기지 않게 했다.
